## 1. 缓存根目录迁移

### 1.1 起因

原路径落在 `Context.getExternalCacheDir()` 里面：

```
/storage/emulated/0/Android/data/com.tencent.mm/cache/WcS
```

微信的「存储空间 → 清理缓存」和系统的「清除缓存」都会清这个目录，导致识别缓存、语音列表全部丢失（其中识别缓存是**花了钱**的）。

### 1.2 决策过程（含一次纠正）

- 最初考虑搬到 `.../WcS/cache`，被否：名字里带 `cache` 仍有被第三方清理工具按名匹配的风险。
- 我一度说「挪 cache 会让 API 配置和音色列表全丢」，**这是错的**：API 配置存在 `WePrefs` → MMKV（`/data/data/com.tencent.mm/files/mmkv/wcs_prefs`），根本不在这。
- 真正会痛的只有两份：`doubao_voices.json`（靠 cookie 能重拉）、`ai-recognition/`（重拉要重新计费）。
- 用户拍板：**不保护、不迁移、不补清理入口**，旧目录自己手动删。

### 1.3 最终改动

只改一处定义，30 处调用点全部走该属性：

```kotlin
// KnownPaths.moduleCache
val moduleCache: Path get() = moduleData / "Wcs_Cache"
// 落地路径：/storage/emulated/0/Android/data/com.tencent.mm/WcS/Wcs_Cache
```

验证方式：`grep '"cache"'` 全仓只命中定义行，无硬编码。

### 1.4 影响面盘点（18 类使用者）

`docs/development/cache-wcs-inventory.md` 记录了全部 18 类使用者，其中三个**确定泄漏点**（只增不删）：

| 泄漏点 | 原因 |
|---|---|
| `upload_*` | ApiServer 8 处调用，全文件无 delete |
| `group_report_*.png` | 发完不删 |
| `auto_save_moments_*.bin` | 转存相册后不删 |

另有 `wcs_moments_img/video_*`、`monet/` 属「有用途无回收」，以及 JavaEngine 把 `cacheDir` 暴露给脚本（脚本可任意写）。

### 1.5 未验证的前提

微信「清理缓存」是否真的**整目录**清掉 `Android/data/com.tencent.mm/cache`，是按 `getExternalCacheDir` 机制推断的，未实测。

## 2. 自动回复实现

### 2.1 文件职责

| 文件 | 职责 |
|---|---|
| `features/items/chat/AiReplyEngine.kt` | 纯生成：吃「批次目标 + 设置快照」，吐单条正文。不读偏好 |
| `features/items/chat/AutoReplyScheduler.kt` | 分桶调度：按 `账号\|会话` 一个 bucket，防抖 / 最长等待 / 冷却 / 全局并发 1 |
| `features/items/chat/AutoReplyLedger.kt` | 去重账本：内存原子领取（2000 条）+ 磁盘 `moduleData/auto_reply/state.json`（500 条） |
| `features/items/chat/AiAutoReply.kt` | 主流程：入站过滤、群聊矩阵、双开关语音、配置页、日志读写 |
| `features/items/chat/AiReplyCandidates.kt` | 配置项取值（节奏、批大小、有效视觉档） |
| `docs/development/ai-auto-reply-design.md` | 设计稿（已同步到实现） |

### 2.2 调度模型

```
入站消息
  └─ 过滤（白名单 / 群聊矩阵 / 自己发的 / 类型支持）
      └─ submit → bucket（ArrayDeque 队列 + CONFLATED 唤醒信号）
          └─ loop：防抖 3s / 最长 15s → 冷却 10s → Semaphore(1) 全局串行
              └─ AiReplyEngine.generate → 发送 → 记账 → 写日志（NonCancellable）
```

节奏档位：防抖 3s / 最长等待 15s / 冷却 10s；批大小 = 「参考上下文条数」（1~20）。

### 2.3 关键设计取舍

| 取舍 | 理由 |
|---|---|
| 超上下文条数**丢最旧**，不排队 | 100 条排出 5 批、每批 60s，第四批回复时内容早过时，追着回旧话比不回更糟 |
| 每会话一个版本号 | 原来用全局版本号，人工接管会误杀其它会话的在途批次 |
| 账本落 `moduleData`（非 cache） | 去重状态不能随缓存清理丢失 |
| 手动候选路径**未改** | 设计稿第 0 节记了这处偏差，手动识别行为保持原样 |

### 2.4 配置页结构

「AI 回复」面板第一组，顺序为：**自动回复 → API 配置 → 语音配置 → 多媒体识别 → 生成参数**（原来 API 在最前，本次一并调序）。

- 自动回复是 `ClickableFeature`（自带总开关 + 点击进配置）；`AiAutoReply` 不注册为 Feature，否则设置页会出现第二个开关。
- 语音双开关**与**关系：`语音配置.开启语音回复` ∧ `自动回复.voice_reply` 才发语音，其余三种组合都只发文字。
- 群聊：`group_enabled` 决定回不回群，`group_at_only` 决定回哪些，`skip_announce_all`（默认开）独立丢弃 @所有人。

### 2.5 日志

```
moduleCache/auto-reply/<账号>/<会话>/yyyy-MM-dd.log
```

- 一行一条 JSON，只留 时间 / 会话 / 结果 / 一句原因；字数、耗时、模型名只进文件不进界面
- 保留 3 天（`RETENTION_DAYS = 3`），启动时 `prune` 按 mtime 删，并清掉白名单变更留下的空目录
- 会话目录名 `sanitize()`：保留字母数字与 `_ - @ .`，其余换 `_`，截 64 字符
- 日志页读「该账号当天全部会话」合并、按时间倒序，界面无需改动（行内本来就有 `talker`）

## 4. 本轮修掉的问题（问题 → 根因 → 改法）

| # | 现象 | 根因 | 改法 |
|---|---|---|---|
| 1 | 配置页「已开启 N 个会话」「回复节奏」选完不刷新 | 直接读 MMKV 的 `prefOption` 委托不建立 Compose 订阅 | 改成可观察 State；`openRhythmDialog` 补 `onDone` 回调（`onDismiss` 在 `onDone` 前会让写状态失效） |
| 2 | 日志有成功记录，界面却一直显示「等待回复」 | `sendText` 走 `postToQueue` 后异步入库，`isSend=1` 被当成人工接管，取消点正好落在写日志之前 | 发送 + 记账 + 写日志整段包 `withContext(NonCancellable)` |
| 3 | 一个会话出事会静默到重启 | `buckets.remove` 写在 `while` 之后，循环体任何未捕获异常都跳过它，留下 job 已死、signal 无人收的僵尸 bucket | `loop` 改 `try { while … } finally { buckets.remove(key, bucket) }`，两参 remove 避免误删接管后新建的 bucket |
| 4 | 视频消息必然失败，还会把同批文字拖死 | 统一走 3 次 × 12s 重试 ≈ 38.1s，而等文件要 15s，每次都被 12s 截断；60s 总预算被吃光 | 视频按「文件是否已落盘」分两条路，见 4.1 |
| 5 | 刷屏时无限积压、追着回旧消息 | 无界 `Channel`；`MAX_BATCH`/`MAX_PENDING` 是死代码 | 有界 `ArrayDeque` + `CONFLATED` 唤醒信号；超限丢队头，日志记 `SKIP / overflow:N` |
| 6 | AI 每发一条都可能被当成「本人手动发言」 | 回声登记在 `sendText` 之后，微信入库可能抢先 | 新增 `markSelfSent` / `consumeSelfEcho`，用正文（群聊按 `wxid_x:\n` 后缀）与语音类型+时间窗认领 |
| 7 | 多媒体识别服务商下拉有「未选择」 | 与语音配置不一致 | 去掉 `api_profile_none`，未选时回退第一条视觉档，无档时红字提示（避免 `options.first{}` 抛异常） |
| 8 | 日志文件在文件管理器可见，设置页全是 0 | `today()` 用不带后缀的 `dateName()` 比对 `isFile`，实际文件名是 `yyyy-MM-dd.log` | 新增 `logName()` 统一生成，写入与读取共用 |

### 4.1 视频的两条路（第 4 条的落地）

先要能**便宜地**判断「下载了没有」。`materializeVideoSource` 不能用来探测——本地没文件时会走 VFS 真拷贝。因此新增：

```kotlin
// WeMessageApi.kt
fun isVideoLocallyAvailable(rawPath: String): Boolean   // 只查文件系统，毫秒级
```

| 判定 | 走哪条路 | 最坏耗时 |
|---|---|---|
| 已落盘 | `runRecognize`（3 次 × 12s），`videoWaitMs = 0` | 38.1s（含 0.7/1.4s 退避） |
| 未落盘 | 单次，等文件 3s，总上限 8s，**不重试** | 3~8s |
| 已落盘但 > 10MB | 每轮立刻 `TooLarge` | 约 2s（只剩退避） |

代价：已落盘的 10MB 级视频在慢网下三次可能都超时，最坏吃 38s，60s 总预算只剩 22s 给模型。

`videoWaitMs` 从 `recognizeForReply` → `recognizeMedia` → `awaitVideoSource(waitMs)` 透传，手动识别路径默认值仍是 15s，行为不变。

## 5. 明确没做的事

| 项 | 现状 |
|---|---|
| 全局频次上限 | 只有 `Semaphore(1)` 保证不并发，不限吞吐；20 个会话同时刷屏 = 20 条连发。设计稿写的「6 次/分钟」代码里没有 |
| 视频自动缓存 / 催下载 | `AutoCacheImages` 只处理图片；`WeMessageApi` 有 `downloadImage/Sticker/Voice/File` 唯独无 `downloadVideo`；`MAX_VIDEO_SIZE = 10MB` 会挡掉多数视频。要做需先反编译找 `IDownloadVideoService` |
| 语音超时双发 | 语音其实已发出但回执超时 → 降级又发一条文字，对方收到两份。概率低但尴尬 |
| 账本全量重写 | `AutoReplyLedger.record` 每次把 500 条全部序列化重写，应改 JSONL 追加 |
| 回声登记时机 | 仍在 `sendText` 之后，窗口很小但非零 |
| 日志导出 / 按会话筛选入口 | 数据已按会话分目录，UI 未接 |
| 静默时段 | 半夜对方发消息照样回 |
| 三个内存 map 无上限 | `cooldownUntil` / `versions` / `echoes`，key 是「账号\|会话」，量级几十到百来 KB，不算泄漏 |
| 旧目录 | `Android/data/com.tencent.mm/cache/WcS` 需手动删 |
| 手动候选路径 | 未按设计稿对齐（设计稿第 0 节已记偏差） |

## 7. 环境备忘（换设备必看）

### 7.1 本机编不了

`D:/android-sdk-lite` 只有 build-tools 34 + platform 34，工程要 **android-37 / compileSdk 37**，且无 cmdline-tools。所以：

- 任何 Kotlin 改动都只能靠 CI 验证，一轮 5~10 分钟
- `local.properties` 需写 `sdk.dir=D\:\\android-sdk-lite` 才能跑 gradle 任务（已 gitignore）

### 7.2 读私有 CI 日志

```bash
TOKEN=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill | sed -n 's/^password=//p')
curl -sL -H "Authorization: Bearer $TOKEN" \
  "https://api.github.com/repos/sherrys8/WCS/actions/jobs/<job_id>/logs"
```

`check-runs/<id>/annotations` 只有 exit code 1，没有编译细节，必须拉 job logs。

### 7.3 踩过的坑

- **后台轮询脚本 exit 0 却被标 failed**：脚本跑完自然退出，看输出里的 `FINAL:` 行判断真实结论，别信任务状态
- **代理**：`github.com:443` 走本地代理 7897，代理挂了会报 `Failed to connect ... over proxy`；`api.github.com` 走另一个端口仍通。api 通、git 不通 = 本地代理没起，不是网络问题
- **漏 import 是最高频的 CI 红**：新增跨包静态调用前先 grep 文件头 import 区。这几轮 CI 失败全是这类「一眼可见但本地验不了」的错误
- 多 agent 并行改同一仓库时，改文件前先读当前内容，别信上次写入的记忆
