# 基于 AI回复与 WeAgent 触发机制实现自动回复的技术方案

状态：自动回复仍为技术分析稿，尚未实现。分析日期：2026-11-19；源码基线：`95f92687`（WCS 分支）。后续根据用户要求，本地已实现手动/自动回复共用的持久化识别缓存并接入现有手动回复，尚未构建或真机验证；不代表自动触发与发送已实现。除明确列出的缓存改动外，本文新增文件、类型、偏好、数值及行为仍为建议。

## 1. 可行性结论

可以实现。现有 AI回复已经具备“历史上下文 + 指定目标 → 媒体识别/语音转写 → 回复模型 → 候选文本”的主要能力，微信文本发送接口也已存在。缺少的是自动触发、任务调度和发送前决策，而不是另一套模型接入。

建议新增独立“AI自动回复”功能：参考 WeAgent 的数据库事件监听、防抖缓冲和冷却思路，抽取 AI回复中不依赖界面的生成能力，最后由程序向原会话发送一条确定的回复。自动功能默认关闭，白名单默认空；手动 AI回复和独立 AI识别的开关不作为自动功能的隐式前提。

不建议以后台打开候选弹窗、模拟点击第一条候选的方式实现，也不建议为了固定聊天回复而接入整个 Agent 工具循环。WeAgent 的触发器可以驱动 Agent 回合，但“触发成功”“Agent 写了回答”和“已向微信联系人发送回答”是三件不同的事。

### 2.1 不能直接套用 WeAgent 的原因

1. **缓冲维度不同**：EventTriggerBus 按 triggerId 建 TriggerBuffer。如果一条规则匹配多个微信会话，事件可能混在同一批中；自动回复必须按“账号 + talker”隔离。
2. **消息身份不足**：TriggeredEvent.Message 使用 Instant.now() 表示观察时间，不能据此恢复原消息时间、媒体路径或稳定去重，也无法准确锚定历史窗口。
3. **没有消息新鲜度检查**：该 MESSAGE 分支未检查 createTime 或稳定消息ID，历史同步/备份导入仍需另设过滤。
4. **忙时行为不同**：WeAgent 的 triggered turn 忙时跳过，不等于“这条微信消息将在稍后被回复”。
5. **回合不等于自动发送**：模型需要决定调用发送工具，且受权限审批影响；普通 assistant 正文写入 Agent 会话，并不会天然发给触发者。
6. **冷却不是完整互斥**：TriggerManager 的检查和 lastFiredAt 写入不是本功能所需的按微信会话原子领取任务，不能把它当作去重/只发送一次的保证。

可以借鉴上述设计，不必修改 WeAgent 的现有行为、数据库实体或 TriggeredEvent 结构。若以后确有多个业务复用，再考虑抽公共缓冲器，首期不先造通用自动化框架。

## 3. 路线比较与推荐范围

| 路线 | 优点 | 主要代价 | 判断 |
|---|---|---|---|
| 配置 WeAgent MESSAGE 触发器，再让模型调用发送工具 | 基础触发和工具已有，适合多步骤任务 | 需要 Agent 模型/会话/权限配置；媒体目标身份不足；发到哪里由工具参数表达；同会话忙时跳过 | 可用于熟悉 WeAgent 的定制任务，不作为此功能的默认实现 |
| 新增自动回复调度，复用 AI回复引擎 | 保留现有上下文和媒体能力，发送目标由程序锁定，配置容易理解 | 需抽取生成能力，新增队列、去重及发送校验 | **推荐** |
| 自动打开现有候选弹窗并点击 | 看似修改少 | 依赖前台窗口和用户交互，无法稳定取消、分会话或后台执行 | 不采用 |

首期完整目标为白名单单聊/群聊中的文字、语音、图片、表情、视频输入，输出一条文本。可以分阶段交付，但不能在只做完文字触发时宣称多媒体自动回复已完成。

不包含工具调用、搜索网页、文件执行、图片回复、自动加好友、定时问候或跨会话转发。自动语音输出另设独立默认关闭开关，建议放后续阶段，不默认跟随手动候选窗口的 TTS 开关。

## 4. 建议结构与边界

```text
WeDatabaseListenerApi 消息插入
  → AiAutoReply：字段快照、账号/方向/白名单/新鲜度过滤
  → 后台按稳定身份还原消息、去重
  → 按 account + talker 缓冲连续消息
  → 每会话单工作任务 + 全局并发闸
  → 共用 AiReplyEngine：历史、目标、ASR、视觉、回复模型
  → 结构化完整性检查
  → 发送前重验账号、开关、白名单、版本和用户接管
  → WeMessageApi.sendText(固定 talker, 单条正文)
  → 记录发送队列接受/失败/结果不明
```

以上 AiAutoReply、AiReplyEngine 是拟新增名称，并非已存在API。建议保持两层：功能对象负责监听、设置和调度；共用引擎负责可取消的生成工作，必要的数据类随引擎放置，不为一次使用引入接口体系。

### 4.1 从 AI回复抽取什么

- 将 requestCandidates 中的媒体准备、历史查询、模型请求和流结束校验抽到无 Compose 依赖的引擎。手动界面只负责读取用户选项、调用引擎、呈现结果和人工发送。
- 引擎接收消息快照、账号、模型/视觉/ASR相关设置快照、语气及输出模式；一次任务中不反复读取可能变化的可变偏好。
- 统一文字目标、语音目标和媒体目标的 prepareTarget。现有目标语音转写位于菜单回调中，必须移出才能被后台调用。
- 返回结构化结果：正文/候选、finishReason、完整性、输入计量、媒体和语音失败明细，而不是只返回 List<String>；自动发送层应知道信息是否缺失。
- 手动候选继续原编号格式和缺结束标记提示，不因自动功能改变现有交互。
- 自动模式直接要求“一条可发送正文，不带候选序号及解释”，不生成三条后随便取第一条。不能沿用 parseNumbered 对任意非空行的宽松回退，以免把解释或多段正文当候选。
- 自动生成请求仍 tools=emptyList；目的会话由触发快照决定，模型输出不能指定新的 talker、命令或发送类型。

### 4.2 配置复用

建议自动功能首期明确标注“使用 AI回复当前模型、语气及上下文设置”，在任务领取时复制为不可变快照。自动开关和会话名单独立；无需复制 API Key 或新建一套服务商管理。

视觉档和识别指令可复用 AI回复当前选择，但自动功能的“识别多媒体”是独立默认关闭开关。关闭时，历史媒体只保留类型；以媒体为目标的自动触发直接跳过，不能照搬手动“目标媒体始终识别”的语义。语音目标也须显式开启自动语音识别；未开启时历史只留语音占位，不后台转写。

若后续需要自动功能独立模型，应新增明确的配置档引用并纳入 ApiProfiles.usageCount，而不是另存凭据。本文不默认实施这一扩展。

## 5. 消息接入、身份与防重复

### 5.1 监听回调只做轻量操作

onEnable 注册监听；onDisable 移除监听，取消本功能 scope/缓冲/任务并使发送许可失效。重新开启时创建新的生命周期版本，不恢复旧任务。

数据库回调中只做表名、启用、账号、方向、类型、白名单和基础时间判断，并复制所需 ContentValues 字段；不得在宿主线程中请求模型、识别媒体、执行长查询或等待。必须检查 isSend 实际存在且为0，不能把缺失方向默认视为收到。

建议快照：account、talker、msgId、msgSvrId、createTime、type、isSend、content、imgPath、observedAt。账号为空、会话为空、消息时间或身份不可用时不触发；收到方群聊需另解析 sender。

因为共享监听没有暴露插入结果和数据库身份，应在后台用当前账号数据库按稳定身份重查真实消息行，并核对字段。有限等待尚未可见的插入行；失败则跳过，不用“同会话最新消息”代替目标。禁止无限轮询等待提交。

还原原生消息可用 getMsgInfoInstanceByMsgSvrId(msgSvrId, talker)，必须传会话；msgSvrId不可用时可局部参数化查询后 convertMsgInfoInstanceFromCursor，不直接调用 private getMsgInfoByMsgId，也不把本地ID冒充服务端ID。是否需要这一路径以实测收到消息的字段为准。

### 5.2 过滤和去重建议

1. 只处理开启之后观察到的新收到消息；不在启用或重启时扫描未读历史补回复。
2. 白名单精确匹配 talker，默认空；文件传输助手、公众号、系统/状态通知等非白名单对象不进入任务。
3. 按已支持类型分流，不将任意 type=49 链接/文件卡片当文字；引用目标只沿用 MessageInfo.humanReadableRepr 的既有能力。
4. 建议收到消息年龄上限30秒，并排除明显未来时间；消息时间与观察时间分开记录。时间归一化沿用已核实的毫秒字段，不盲目猜单位。
5. 去重键优先 account + talker + msgSvrId；缺少服务端ID时使用 account + talker + msgId。两种ID同时存在时记录别名，避免补齐服务端ID后再处理一次。
6. 去重领取、入队和版本更新必须在同一会话的原子临界区执行；不能采用 contains 后 put 的竞态写法。
7. 不以“正文相同”去重，对方连续两次发相同内容仍是不同消息。普通数据库更新不作为新触发入口。

新鲜度过滤只能降低旧同步触发概率，不能证明一定不是历史导入。验收需覆盖真实离线同步；若宿主将旧消息改成当前时间，现有字段不足以判别，应记录为限制，不能宣称完全识别。

## 6. 会话调度、连续消息与人工接管

建议参数：静默防抖3秒、最长等待15秒、每批最多20条；按账号+talker分别缓冲。同会话串行，全局初始只允许1个生成任务，避免同时触发多个ASR/视觉请求。后续并发调整需先处理共享缓存和临时文件冲突。

批上限是调度分批，不是媒体数量截断：达到20条就形成一个批次，后续消息进入下一批；批内所有启用的媒体都处理。不改变手动 AI回复窗口内全处理的约定。

- 空闲时：防抖结束领取批次，保存目标集合、触发版本、设置快照；发一条回应整批的文本。
- 生成中又来新消息：先进入该会话 pending，不并发生成。建议当前结果若已过时则丢弃，之后将未回复目标和 pending 合并/分批重新生成，避免对新要求发旧答复；仅丢弃旧结果不能将原批标为已回复。
- 持续刷屏：合并仍受批上限、待处理容量和有效期约束；不能无限增长内存，也不应无限取消/重启付费请求。首期建议会话最多保留40条待处理、超限暂停该会话并记录原因，停止继续接单，等用户处理或重新启用。
- 建议任务有效期5分钟，包含排队、媒体准备和生成；超时整批终止并标记过期，不把未处理媒体静默丢掉后发送半成品。该限制仅属于建议的自动模式，需与大批视频耗时的取舍一起确认。
- 用户自己在该会话发送消息：视为接管，增加 takeoverVersion，清空旧缓冲并取消旧任务；只影响该会话。后续真正新收到的消息再按新批次处理。
- 自动发送产生的 isSend=1 也会回流，必须先用发送任务状态/实际消息标识关联自己的发送，再决定是否为人工接管，不能只凭正文完全相同判断。无法关联时保守按接管处理，不产生第二次回复。
- 发送临界区内再次检查版本；生成期间有新消息时不能只在任务开头检查一次。数据库新事件与宿主实际发送之间不存在跨系统事务，仍有极小竞态窗口，不能承诺绝对不发生交叉回复。
- 首期不做跨进程常驻服务、唤醒微信或重启自动补发。只有微信主进程存活、模块/API已就绪且网络可用时处理。

冷却建议单会话10秒，冷却期新消息合并等待而不是直接丢弃；另设全局每分钟最多6次模型回复启动，视觉/ASR调用量另计。程序应同时统计实际模型调用次数和消息发送次数，不能拿 WeAgent 的“每分钟新建会话数”代替费用限制。

## 7. 上下文、多媒体与群聊语义

### 7.1 防止历史与批次重复

自动批次中的消息按 createTime、msgId 排序并全部保留一次，最新消息作为本批最终锚点。建议模型输入为：

```text
SYSTEM：本人语气 + 单条回复格式 + 聊天数据边界
USER：
  历史记录（从旧到新，严格早于本批最早目标）
  本次待回复消息（从旧到新，含发送人和各条类型/识别结果）
  请以本人身份对以上待回复消息作出一条自然回复
```

历史先按本批最早目标前的边界查询，再按现有N条/7天窗口整理；不是针对最后一条查历史后再追加全部目标，否则前几条目标会出现两次。批次目标不受历史N条挤掉，N=0只去掉历史；批次内部最新消息会覆盖较早约定，例如先“十点东门”后“三点西门”。

历史文字/语音每条300字符、目标文字/语音每条300字符可暂沿用，必须在快照中明确；媒体描述不截300，单视频10MiB、动画最多六幅采样等限制沿用现有底座。自动批次与历史总量、服务商上下文容量需校验，超限终止并记录，不能伪报模型已看完。

### 7.2 识别失败与缓存

- 目标语音/媒体未下载、转写/识别失败：默认整批不自动发送，避免仅凭类型占位猜答。未启用的类型不进入目标批次。
- 历史识别失败：保留失败明细；建议自动模式默认也不发送该批，手动模式仍保留现有“占位后继续”行为。以后如提供容错选项，必须明确告知可能缺少上下文，不自动默认开启。
- 不主动替用户播放视频。可复用已有等待落盘/VFS路径处理；取不到就失败。前一轮测试中未下载视频失败、播放后重试成功，说明自动场景仍需面对媒体尚未落盘。
- 401/403/429、模型空结果、超时不反复重试，不向对方自动发送内部异常。首期单次失败只记录；配置类错误应暂停触发并在本功能设置中提示。
- 按用户后续要求，已新增共用 AiRecognitionCache，成功的语音转写、图片/表情/视频分析文本保存在 KnownPaths.moduleCache / ai-recognition / 账号SHA-256 / 缓存键SHA-256.json。当前微信对应 `/storage/emulated/0/Android/data/com.tencent.mm/cache/WcS/ai-recognition/`，路径由既有工具推导，不硬编码到源码。
- 账号、会话、服务端消息ID（没有则本地ID）、消息类型/时间、模型配置摘要及识别指令参与隔离。配置摘要包含凭据变化，但磁盘不保存Key/Cookie或完整配置；缓存文件只保存版本、类别、时间和返回文本。按手机本地日期及缓存文件最后修改时间保留今天及之前3天；进程内首次使用或跨天访问时清理各账号目录中更早的JSON，读取也拒绝过期结果。命中不刷新日期；过期或被用户/系统清理后重新识别，不设200条淘汰。
- 入口为 AiImageRecognition.recognizeForReply、VoiceTranscriber.transcribe 和 transcribeByEncPath，未来自动回复必须调用相同入口，而非自行直接发视觉/ASR请求。重开弹窗或重启仍可复用；识别前先查缓存，命中无需重新读取原媒体，失败或空结果不写入。
- 共用缓存以分片Mutex串行化相同键的查找与识别，临时文件写完后同目录rename发布，避免并发重复请求及半写入的JSON。无账号时不运行识别；有账号但消息无稳定身份时不缓存。账号变化或任务取消后不写入新结果。
- VoiceTranscriber 已改用同一缓存，不再读取缺乏账号/模型信息的旧 ai_stt_cache.json（不删除旧文件）；网络请求使用获取缓存键时的同一ApiProfile快照，转码临时文件改UUID，避免与手动识别并发时覆盖。修改识别配置或指令会产生新缓存，旧成功结果仍保留。
- VoiceTranscriber 的网络是同步 execute，不能把外层协程取消等同于HTTP立即停止。应给自动任务补可取消调用绑定，并在转码前后、缓存写入和回调发送前验证任务仍有效。

### 7.3 群聊

建议“群聊自动回复”另设默认关闭开关，仍需精确群白名单；首期仅接受真实@本人触发，@所有人不自动视为@本人，避免普通群聊每条都回复。

结构化提及可参考 MessageInfo.mentionedUsers（`MessageInfo.kt:110–118`），但须实测收到消息的 lvbuffer/msgSource 是否齐全；无法确认时不触发，不以昵称文本或包含@字符作为替代。

同一群不同发送者必须保留 sender 和显示名，不能全写“对方”。仅@本人的消息进入目标批，其他群消息可作为历史；本人手动发言触发接管。是否引用发送、是否自动@原发送人是额外产品选择，建议首期普通文本、不自动@，并发多成员测试通过后再扩大范围。

## 8. 完整性校验、自动发送和日志

### 8.1 自动发送门槛

自动模式只接受 Completed、非空正文以及已识别的正常 finishReason（stop/end_turn/stop_sequence，统一大小写）。现有手动模式允许 finishReason缺失时展示候选并提示，自动模式不能直接放行；返回 length、过滤、中断或未报告结束原因时均不发送。若某适配器有等价协议级完成证据，应在适配器处明确映射后再支持，不能简单删除校验。

正文应满足单回复输出约定和建议的长度上限（如1000字符），不得发送推理增量、候选列表、模型解释或空串。多段自然正文不应被 parseNumbered 拆成多次发送；超限或无法确定输出形态时记失败，不靠危险的截断/宽松回退。

发送前重验：账号未变、自动总开关与相应类型开关仍开、会话仍在白名单、依赖API已就绪、任务未过期/取消/被新消息替代、没有人工接管、去重账本未标发送过、模型结果完整。配置在生成中变更时令旧快照任务失效，下一批用新配置。

调用固定 talker 的 sendText，不使用当前打开聊天的目的地，不让模型返回发送对象。引用回复可后续接入 sendQuoteTextByMsgId；引用失败是否回落普通文本须显式规定，不能可能已经发送后再无条件重发。

### 8.2 发送语义和去重账本

建议状态：OBSERVED → BUFFERED → PREPARING → GENERATING → READY → SENDING → QUEUE_ACCEPTED；另有SKIPPED、FAILED、CANCELLED、SUPERSEDED、EXPIRED、SEND_UNKNOWN。记录任务ID、账号/会话身份和目标ID集合，媒体阶段单独记进度。

在调用宿主发送前持久化SENDING及批次ID；返回true只标QUEUE_ACCEPTED。进程崩溃、异常或结果不明确时标SEND_UNKNOWN，重启不自动重发；没有服务端回执关联前不标DELIVERED。程序只能降低重复风险，无法仅靠sendText(Boolean)保证端到端exactly-once。

自动发出的微信消息再次入库时，按目标ID去重、isSend过滤及本功能发送关联阻止回环。两端都启用机器人仍可能你来我往，单会话冷却、频次和待处理上限用于约束；不承诺判断对面是否机器人。

### 8.3 可观察性

设置中显示最近任务时间、阶段、跳过原因、媒体/语音成功失败数、finishReason、模型输入计量、排队/生成耗时和宿主队列接受结果。发送失败不在聊天里泄露服务地址、凭据或内部错误。

默认日志不写完整聊天、语音转写、视觉描述、请求体、回复正文或Key/Cookie。现有 WeMessageApi.sendText 会记录正文，实施时需增加仅作用于自动路径的脱敏调用选项，默认参数保留原调用方行为；不能只保证新模块日志脱敏而忽略发送底层。

如果用户需要排查输入事实，可后续提供显式启用、短期留存的本地诊断，首期不默认持久化聊天内容。promptTokens只能证明服务端计量，不能当成每条媒体均被理解的回执。

## 9. 设置界面与建议默认值

使用 ClickableFeature 的开关+点击设置入口，沿用 SegmentedColumn、SwitchWidget、ContactsSelector、TextFieldDialogWidget 和范围选择控件；变更即时生效，Compose行值以本地状态同步偏好。以下均为建议，不是现有设置。

| 设置 | 建议默认 | 语义 |
|---|---|---|
| AI自动回复总开关 | 关闭 | 与手动AI回复、独立AI识别、WeAgent独立启停 |
| 生效会话 | 空白名单 | 单聊/群聊均需明确选入 |
| 回复模型/语气/历史窗口 | 使用AI回复设置 | 明确展示跟随关系，任务开始时快照 |
| 自动语音识别 | 关闭 | 开启后才处理语音目标及历史转写，需ASR配置 |
| 自动多媒体识别 | 关闭 | 开启后才处理媒体目标及历史识别，复用指定视觉档 |
| 群聊自动回复 | 关闭 | 开启后仅对白名单群的真实@本人消息触发 |
| 输出方式 | 一条文字 | 自动语音、引用或自动@均不默认为开启 |
| 连续消息防抖/最长等待 | 3秒 / 15秒 | 分会话合并，数量阈值20条 |
| 会话冷却 | 10秒 | 合并等待，不能等同于忙时丢弃 |
| 手动发言接管 | 固定启用 | 废弃旧任务，后续新入站消息才可再次触发 |

新功能偏好建议统一 ai_auto_reply_ 前缀；配置变化版本、生命周期版本、账号和会话维度共同参与发送有效性校验。删除配置档的引用检查沿用已有管理机制，不能让自动后台继续握持已删除配置发送。

## 11. 验收清单与当前验证边界

| 场景 | 通过标准 |
|---|---|
| 总开关关闭/白名单为空 | 不请求模型、不识别媒体、不发送 |
| 单聊白名单/非白名单 | 只有指定会话触发，切换当前聊天不会改发送对象 |
| 自己发消息/自动消息回流 | 不触发新的自动回复；手动接管使旧结果作废 |
| 重复回调/ID补齐/数据库更新 | 同一消息只领取一次；普通更新不触发补回复 |
| 旧记录导入/离线同步/重启 | 不批量补回复，记录无法判别的同步限制 |
| 一人连续发/两会话同时发 | 各自合并，绝不混会话；同会话不重入 |
| 生成中更正时间地点 | 旧答复不继续发送，新任务保留未回复目标并采用最新约定 |
| 生成中用户手动回复/关开关/删白名单/换账号 | 旧结果不得再进入发送；隔离其他会话任务 |
| N=0/同时间戳/批次跨历史窗口 | 目标完整且只出现一次；历史旧到新，不带锚点后的消息 |
| 超过3条混合媒体 | 批内所有启用媒体被尝试，无隐式媒体数量截断 |
| 未下载视频/ASR500/视觉401或429 | 不发送猜测正文，不循环重试，不给对方发内部错误 |
| 流中断/缺finishReason/length/空正文 | 自动模式不发送；手动原提示与候选行为不回归 |
| 多段回复/编号候选/推理输出 | 一条自然正文才能发送，不多发列表、不发思考内容 |
| 宿主入队true/false/进程中断 | 区分接受、失败、未知；未知重启不自动重发，不宣称送达 |
| 群聊 | 默认不触发；启用后只对白名单群真实@本人触发，成员身份不混 |
| 长时间运行/刷屏/对面也是机器人 | 并发、冷却、队列和频次受控，关闭可停止后续动作 |
| 手动/自动ASR并发 | 不共用临时文件、不覆盖账号缓存，取消后不误回调发送 |
